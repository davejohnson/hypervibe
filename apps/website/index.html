$ hypervibe --explain-loop
01 spec set

Declare the desired state — services, databases, storage, domains, email, env vars — as a revisioned spec committed with your repo.

02 plan

Observe live infrastructure, diff against the spec, and get an executable plan. No surprises: every action is listed before anything runs.

03 apply

Converge. Stale plans are rejected. Destroying data-bearing resources requires explicit per-action confirmation.

04 status

Read-only drift view. See exactly where live infrastructure has wandered from desired state, at any time.

Terraform-style discipline, zero YAML. The persisted plan is an authorization boundary — an apply can only touch what its reviewed actions name.

$ hypervibe features --all

CLI ⇄ MCP parity

Every command works from your shell or from Claude / Codex as an hv_* tool. Human-readable output by default, stable redacted JSON with --json.

Auto-wiring

Provision a Postgres and DATABASE_URL lands in the right services automatically. Queues, buckets, and webhook secrets wire themselves the same way.

Team-shared state

Desired state lives in .hypervibe/spec.json, committed with the app. Teammates clone, plan, and converge the same resources — no private local state.

Secrets done right

Vault, AWS Secrets Manager, Doppler, 1Password, Bitwarden. Rotate once, propagate everywhere. Values never appear in specs, plans, or tool output.

CI push deploys

Generated GitHub Actions workflows call provider APIs directly. Failed deploys leave redacted evidence artifacts for autofix agents to consume.

Environments

Staging, production, PR previews. Migrations via Prisma / Drizzle / TypeORM. Local parity with generated Docker Compose.

DB diagnostics

Query managed Postgres without exposing it permanently — temporary proxies and scoped ingress that Hypervibe creates and cleans up itself.

iOS releases

Gated TestFlight releases in GitHub Actions: server deploy evidence, SHA-matched builds, App Store credentials scoped to a single reviewed step.

Fuzzy stuff → LLM

Tools return raw data; your agent interprets it. No hardcoded pattern matching — Claude figures out that prod-us-east means production.

$ hypervibe --quick-start

[1] install the CLI

$ npm install -g @davejohnson/hypervibe@latest $ hypervibe --help

[2] or add it to Claude Code as an MCP server

{ "mcpServers": { "hypervibe": { "command": "npx", "args": ["-y", "@davejohnson/hypervibe@latest"] } } }

[3] or add it to Codex

$ codex mcp add hypervibe -- npx -y @davejohnson/hypervibe@latest

[4] connect providers & ship

You: "Connect to Railway"
Claude: Opens browser for Railway OAuth, saves credentials securely.
You: "Deploy my app to staging with a postgres database"
Claude: Creates the project, provisions Postgres, wires DATABASE_URL,
        deploys your code, sets up health checks, returns the URL.

Hypervibe is currently distributed as a private package via GitHub Packages — see the README for token setup. All state stays local: SQLite in ~/.hypervibe, secrets encrypted at rest. Nothing is sent anywhere except the providers you connect.
