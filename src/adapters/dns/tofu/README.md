# DNS engine configuration

These backends generate OpenTofu configuration for records in an existing,
independently observed zone. DNS selection does not depend on hosting selection.
They support A, AAAA, CNAME, TXT, CAA and MX. Cloudflare owns individual record IDs;
Cloud DNS, Route 53 and Azure DNS own the complete name/type record set.

The application must supply fresh `absent`, exact `managed`, or explicitly approved
`adopt` authority. In particular, Cloud DNS creates are authoritative: a matching
name is not proof of absence or permission to overwrite. Adoption retains every
observed value in desired or preserved values. Managed record sets must keep the
persisted preserved values on later plans. CNAME conflicts, inconsistent TTLs and
mixed authority within a record set are rejected. Route 53 overwrite-on-create is
disabled. Azure automatic resource-provider registration is disabled because it
would mutate infrastructure during a read or plan.

`retiredRecords` retains exact address mappings for reviewed removal. An owned
record set with preserved sibling values remains declared with those values only
and is labeled as a retained shared record set. Teardown therefore verifies
absence of the app's owned values, while preserving the shared record set and its
engine ownership. No engine state is forgotten or edited to release ownership.

`DnsZoneIdentity.zoneId` is Cloudflare's zone ID, Route 53's hosted-zone ID,
Azure's full ARM zone ID, or Cloud DNS's managed-zone resource name. Google also
has an immutable numeric managed-zone ID: the observer records this as
`providerNativeId` and the application must compare it before apply so that a
same-named replacement does not acquire old authority. All identities carry their
account/project/subscription scope. These functions cannot establish remote
ownership and do not replace the application observer or apply-time checks.

No zone creation, DNSSEC setting, registrar change, private-zone attachment,
DNS migration or cloud write is hidden in this configuration layer. TLS and
custom-domain readiness belong to the application workflow. Requiring an
unsupported control must produce a blocker there.

## Existing DNS consumers

The shared application bridge stages GitHub Pages and SendGrid DNS from records
frozen by their ordinary read-only planning. Pages first attaches its hostname,
then DNS is planned, then certificate readiness can continue. This follows
[GitHub's hostname-claim ordering](https://docs.github.com/en/pages/configuring-a-custom-domain-for-your-github-pages-site/managing-a-custom-domain-for-your-github-pages-site#about-custom-domain-configuration).
Cleanup removes and verifies owned DNS while the exact repository still claims
the hostname. Only a saved, verified DNS removal receipt authorizes detaching
Pages. An absent or unknown Pages site cannot authorize record deletion.

SendGrid domain authentication must be bound and freshly observed before its
complete automated-security record set can be frozen. The engine also supports
the inbound MX record. The exact authorization ID and returned targets are
checked again before apply. Legacy or incomplete SendGrid DNS layouts stop.
Cloudflare Email Routing's automatic DNS activation remains blocked until its
exact DNS resources have an engine capability; destinations and routing rules
retain their existing separate workflow. Historical Pages/email DNS actions
cannot perform direct provider record writes.

## Verified evidence

`dns-provider-validation.test.ts` runs the actual pinned OpenTofu runtime against
all four pinned providers in normal `npm test`. It validates all six record
shapes, exact import configuration, literal TXT escaping and scoped read probes.
It needs no cloud credentials and performs no cloud writes. This proves provider
configuration compatibility, not live apply, import or DNS propagation.

Provider checksums were generated by managed OpenTofu 1.13.9 using
`providers lock -platform=darwin_arm64 -platform=darwin_amd64
-platform=linux_arm64 -platform=linux_amd64`; OpenTofu verified upstream archive
signatures. Google reuses the existing Google 8.9.0 requirement and checksums.
