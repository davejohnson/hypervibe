# Backup and restore authority

Paths are relative to the repository root. Read when the matching task in `AGENTS.md` applies.

- Default backup intent must cover every persistent database, declared or retained service mount, and object bucket through the shared provider contract. Preserve stronger native schedules, retention and PITR; an explicit exclusion never disables or deletes existing protection. Keep policy configuration, an available recovery point and a tested restore separate, and report unsupported or unknown coverage instead of treating versioning, replication or an empty action list as a backup. Resolve implicit defaults without rewriting legacy deployment hashes; an outstanding checkpoint retains its isolated priority.
- Before a backup mutation, persist its exact scoped source and unique operation identity. An uncertain acknowledgement must never trigger an automatic second backup. Confirm completion through the provider's terminal operation and the matching backup inventory, keep provider snapshots distinct from tested restores, and never use a source-volume restore as a harmless verification step.
- Recurring recovery programs require exact published source/destination identities and a pinned helper artifact. Keep schedule, retained-point and restore evidence separate; verify fresh readiness before rollout writes and report prerequisite-only applies as pending. Re-observe native source identity in scheduled consumers as well as local planning. A selected resource ID does not attenuate a credential: require provider-proven credential scope before private-worker handoff. Write completion last, attest provider cleanup separately, and never count partial sets toward retention or healthy alerts. A database/files set must verify the restored database's references against retained file bytes; successful independent copies do not establish application consistency.
- Bind prior restore proof to native revisions captured from checksum-verified retained bytes. Check those revisions during health and whenever fresh inventory becomes conditional-delete authority; matching names and lengths cannot detect same-size replacement. Version stronger evidence formats, retain historical contracts without certifying or deleting them, and never invent missing historical proof.
- Admit provider combinations through shared capability metadata, not the independent existence of two adapters. Validate the current destination selection and helper artifact at execution time, and test the published helper's authentication contract through its real consumer. Missing cleanup proof and ambiguous mutation counts remain unknown, never implicit success or zero writes.
- Define persisted safety evidence with one runtime schema and derive its type from that schema. Producers, completion coordinators and later health/retention readers must validate the same contract; selected-field checks can accept incomplete or contradictory proof. Exercise a real producer through those consumers and reject altered coverage or verification claims before granting readiness or deletion authority.
- Cross-cutting deployment gates must preserve reviewed prerequisite stages without admitting workload or data writes. Test namespace creation, empty service identity, storage preparation, source disconnection and workflow publication alongside blocked ordinary deployments. Carry creation-only authority through provider execution and reject an existing workload before environment or configuration mutation; an earlier observation cannot authorize a later update. Existing protected-resource fixtures must supply scoped prerequisite evidence at the adapter boundary; do not disable the policy or mock its gate to keep unrelated assertions passing. No infrastructure drift does not imply recovery readiness.
- Dependency edges must represent actual prerequisites. Exercise initial data-resource provisioning while accepted CI workflows still need credential or binding synchronization; removing those actions from a fixture hides bootstrap deadlocks. Keep workload gates and real namespace/database dependencies intact. Follow the real credential and repository-publication planners through to a runnable recovery workflow, including a separate canonical repository environment; a blocked rollout alone does not prove setup can finish.
- Classify prerequisite failures separately from missing connections at their source. Plan, apply and deploy must preserve that distinction; only actual connection failures may produce credential setup instructions, including when both kinds are present.
- Portable execution authority must compare its source against a current, strict non-secret binding export. Refresh that export on component creation, replacement, binding updates and removal; checking only the provider name permits an obsolete resource to keep producing apparently healthy receipts. For an already-authorized portable storage binding, re-observe its exact native identity and account/project scope; a checkout's local ID must not replace either.
